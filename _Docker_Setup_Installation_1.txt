The Docker daemon binds to a Unix socket, not a TCP port. 
By default it's the root user that owns the Unix socket, and other users can only access it using sudo. 
The Docker daemon always runs as the root user.

If you don't want to preface the docker command with sudo, create a Unix group called docker and add users to it. 
When the Docker daemon starts, it creates a Unix socket accessible by members of the docker group.

sudo groupadd docker

By default, the Docker daemon (the engine) runs as the root user, meaning only root can talk to it. 
The docker group allows specific non-root users to communicate with the engine without using sudo every time.

In Linux, Docker communicates through a Unix domain socket located at /var/run/docker.sock. Think of this socket as the "door" to the Docker Engine.
Ownership: When the Docker service starts, it sets the ownership of that socket file to root:docker.
Permissions: It grants read and write permissions to the owner (root) and the group (docker).
The Link: When you add a user to the docker group, that user inherits the right to "write" to that socket. 
When you type docker run, your command travels through that socket to the daemon, which then executes the request as root.

The docker group primarily grants rights to the daemon API, not necessarily all the files on your hard drive. However, it does grant access to:
/var/run/docker.sock: As mentioned, this is the most critical file.
/var/lib/docker: This is where images and containers live. While usually restricted to root, the daemon handles the file manipulation here on behalf of any user in the docker group.

When we run docker ps.
Identity Check: The system checks if your user ID is part of the docker group in /etc/group.
Socket Access: Because you are in the group, you are allowed to send the "ps" request to /var/run/docker.sock.
Daemon Action: The Docker Daemon (running as root) receives the request, gathers the info, and sends it back to you.


TCP sockets are for talking over a network (even if it's just to your own machine), while Unix sockets are for high-speed communication between processes on the same local machine.
TCP Sockets (Network-Based)
These use the IP stack and are identified by an IP address and Port number (e.g., 127.0.0.1:80).
Scope: Can communicate between different computers or locally (via localhost).
Overhead: Higher. The data has to go through the full network stack (routing, checksums, headers, etc.), even if it's staying on the same machine.
Reliability: Very high across networks, but slightly slower for local-only tasks.
Unix Sockets (File-Based)
These are identified by a file path on the disk (e.g., /var/run/mysql/mysql.sock).
Scope: Local only. They cannot communicate with other machines.
Overhead: Very low. Since the data never leaves the kernel, it skips the network headers, routing, and checksums. This makes them roughly 30% faster than TCP for local traffic.
Security: Better for local use. You can use standard Linux file permissions (read/write) to control which users can access the socket.

Note the docker and containerd service is running on Unix socket so we cannot check its service using the below.


Docker Socket (/var/run/docker.sock) 
This is the entry point for you, the user. 
Purpose: It is the API "front desk." When you type docker run or docker ps, the Docker CLI sends that command through this socket file.
Who listens? The Docker Daemon (dockerd).
Permissions: As we discussed, this file is owned by root:docker. Access to this socket is what gives you the power to manage containers. 
Containerd Socket (/run/containerd/containerd.sock) 
This is the internal line used by the system itself. 
Purpose: Docker doesn't actually "run" containers anymore; it hands that job off to containerd (a lower-level manager). The Docker Daemon acts as the boss, and it sends instructions to containerd through this second socket.
Who listens? The containerd service.
Flow: Your Command → docker.sock → Docker Daemon → containerd.sock → Containerd → Starts Container. 
Why use Sockets instead of Network Ports (TCP)?
Security: A Unix socket is a file. You can use standard Linux permissions (chmod/chown) to control exactly who can touch it. A network port is much harder to "lock down" from other users on the same machine.
Speed: Because it doesn't have to wrap data in network headers (like TCP/IP), communication is slightly faster and uses less CPU.
Local Only: By default, a socket cannot be accessed from outside the server, making it "secure by default."
