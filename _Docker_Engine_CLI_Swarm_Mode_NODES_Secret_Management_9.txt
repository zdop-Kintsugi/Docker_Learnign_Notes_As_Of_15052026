DOCKER SENSITIVE DATA MANAGEMENT WITH DOCEKR SECRECTS


Docker Secrets, a secure storage system for sensitive information (like passwords or API keys) within a Docker Swarm cluster.
In simple terms: instead of hardcoding a password into your code or a Dockerfile (where anyone with access can see it), you give the password to Docker. Docker encrypts it and only "hands" it to the specific containers that need it, right when they start running.

In a production Swarm, you would do this :
Create the Secret : You run a command to upload the password to the Swarm manager. It’s immediately encrypted.Grant Access : In your deployment script, you tell Docker: "Only the 'Web-App' service is allowed to see the 'db_password' secret."
Runtime Injection : When the 'Web-App' container starts, Docker creates a temporary, encrypted file at /run/secrets/db_password inside that container's memory (RAM disk). It never touches the hard drive.App Consumption : Your code looks at that file path to get the password and connect to the DB.

This is a huge win for CI/CD pipelines.In Dev, you create a secret named db_password with the value dev-pass.In Prod, you create a secret named db_password with the value Super-Secure-2026!.
The Benefit : You use the exact same Docker image in both places. The code just asks for the secret named db_password, and Docker handles giving it the right value based on which environment it’s running in.


Encryption : Secrets are encrypted "at rest" (on disk) and "in transit" (over the network).
Least Privilege : If you have 10 services but only 1 needs the SSL certificate, only that 1 gets it.
Memory Only : Once the container stops, the secret vanishes from that node's memory.

Docker manages secrets
Secrets are transmitted over mutual TLS to the swarm manager and stored encrypted in the Raft log, replicated across managers for high availability. Containers access secrets via /run/secrets/<name> (Linux) or C:\ProgramData\Docker\secrets (Windows). Secrets are flushed when tasks stop. You can update services to add/remove secret access dynamically.
Use case: A fintech company deploys payment services where API keys are mounted only at runtime, ensuring they vanish when containers stop, reducing risk of leakage.

You can use secrets to manage any sensitive data which a container needs at runtime but you don't want to store in the image or in source control, such as:

Usernames and passwords
TLS certificates and keys
SSH keys
Other important data such as the name of a database or internal server
Generic strings or binary content (up to 500 kb in size)

Docker secrets are only available to swarm services, not to standalone containers.
The secret is stored in the Raft log, which is encrypted.

Docker sends the secret to the swarm manager over a mutual TLS connection. The secret is stored in the Raft log, which is encrypted. The entire Raft log is replicated across the other managers, ensuring the same high availability guarantees for secrets as for the rest of the swarm management data. You can update a service to grant it access to additional secrets or revoke its access to a given secret at any time.

Docker secret commands :
Docker provides commands like docker secret create, inspect, ls, and rm to manage secrets. Services can be updated with --secret-add or --secret-rm. You cannot remove a secret in use, but you can rotate it by versioning names.
Use case: A production team rotates database passwords monthly by creating db_password_v2, updating services to use it, then removing db_password_v1 once migration is complete.


Redis with Secrets : 
This example demonstrates the basics of creating and using a secret.

A secret (my_secret_data) is created using docker secret create.

A Redis service is launched with access to that secret.

The secret is automatically mounted inside the container at /run/secrets/my_secret_data.

You can verify its presence by running docker exec inside the container.

The secret disappears if you commit the container or remove access via docker service update.

Secrets cannot be removed while in use by a running service.
Production use case: A company deploying Redis in production stores sensitive connection strings or API tokens as secrets. This ensures credentials are never baked into the image or exposed in logs, but are still available at runtime for the service.

Create a secret

printf "This is a secret" | docker secret create my_secret_data -

Create a Redis service with access to the secret

docker service create --name redis --secret my_secret_data redis:alpine

Check if the service is running

docker service ps redis

Find the container ID of the Redis task

docker ps --filter name=redis -q

List secrets inside the container

docker container exec $(docker ps --filter name=redis -q) ls -l /run/secrets

Read the secret file inside the container

docker container exec $(docker ps --filter name=redis -q) cat /run/secrets/my_secret_data

Commit the container (to show secrets aren’t persisted)

docker commit $(docker ps --filter name=redis -q) committed_redis

docker run --rm -it committed_redis cat /run/secrets/my_secret_data

List all secrets

docker secret ls

Try removing the secret (fails because Redis is using it)

docker secret rm my_secret_data

Remove access to the secret from the Redis service

docker service update --secret-rm my_secret_data redis

Verify secret is no longer accessible

docker container exec -it $(docker ps --filter name=redis -q) cat /run/secrets/my_secret_data

Remove the Redis service

docker service rm redis

Remove the secret

docker secret rm my_secret_data

Production use case:  
This workflow is often used when deploying a caching service like Redis in production. For example, a fintech company might store sensitive API tokens or database connection strings as secrets. They mount them only at runtime, verify they’re accessible, and ensure they’re removed when services stop — preventing accidental leaks in logs or committed images.


Nginx with TLS Secrets :
This example shows how secrets can manage certificates and configs for HTTPS.

TLS certificates and keys are generated (or obtained via Let’s Encrypt).

These files (site.key, site.crt, site.conf) are stored as Docker secrets.

An Nginx service is created with access to these secrets, mounting them at /run/secrets or directly into /etc/nginx/conf.d/.

This allows Nginx to serve HTTPS traffic without embedding sensitive files in the image.

Secrets can be rotated easily (e.g., replacing expired certificates) without rebuilding the container image.

Verification is done by accessing the Nginx service over HTTPS and checking the certificate chain. :
Production use case: An e-commerce site uses Docker secrets to manage SSL certificates for Nginx. When certificates expire, they rotate them seamlessly without downtime, ensuring secure customer transactions.

Generate a root key :

openssl genrsa -out "root-ca.key" 4096

Generate a CSR using the root key :

openssl req -new -key "root-ca.key" -out "root-ca.csr" -sha256 -subj '/C=US/ST=CA/L=San Francisco/O=Docker/CN=Swarm Secret Example CA'
 
Sign the root certificate :

openssl x509 -req -days 3650 -in "root-ca.csr" -signkey "root-ca.key" -sha256 -out "root-ca.crt" -extfile "root-ca.cnf" -extensions root_ca 

Generate the site key :

openssl genrsa -out "site.key" 4096
 
Generate the site CSR :

openssl req -new -key "site.key" -out "site.csr" -sha256 -subj '/C=US/ST=CA/L=San Francisco/O=Docker/CN=localhost'

Sign the site certificate :

openssl x509 -req -days 750 -in "site.csr" -sha256 -CA "root-ca.crt" -CAkey "root-ca.key" -CAcreateserial -out : "site.crt" -extfile "site.cnf" -extensions server

Store files as secrets : Create secrets for key, certificate, and config 

docker secret create site.key site.key
docker secret create site.crt site.crt
docker secret create site.conf site.conf

List secrets :

docker secret ls

Create and run Nginx service : Create Nginx service with secrets (using symlink)

docker service create \
  --name nginx \
  --secret site.key \
  --secret site.crt \ :
  --secret site.conf \
  --publish published=3000,target=443 \
  nginx:latest \
  sh -c "ln -s /run/secrets/site.conf /etc/nginx/conf.d/site.conf && exec nginx -g 'daemon off;'"

Alternative: Create Nginx service with custom target

docker service create \
  --name nginx \
  --secret site.key \
  --secret site.crt \
  --secret source=site.conf,target=/etc/nginx/conf.d/site.conf \
  --publish published=3000,target=443 \ :
  nginx:latest \
  sh -c "exec nginx -g 'daemon off;'"

Verify service : Check service status

docker service ls

docker service ps nginx 

Verify HTTPS connection

curl --cacert root-ca.crt https://localhost:3000

Inspect certificate with OpenSSL :

openssl s_client -connect localhost:3000 -CAfile root-ca.crt

Cleanup :

Remove Nginx service

docker service rm nginx

Remove secrets

docker secret rm site.crt site.key site.conf

Production use case:  
An e-commerce platform uses this workflow to manage TLS certificates for Nginx. By storing certificates and configs as secrets, they can rotate expiring certs without rebuilding images, ensuring secure HTTPS connections for customers at all times.

TLS Certificate Rotation with Docker Secrets (Nginx)

Generate a new TLS certificate and key  

Use openssl or a service like Let’s Encrypt to create the new certificate (site_v2.crt) and key (site_v2.key).

openssl genrsa -out "site_v2.key" 4096

openssl req -new -key "site_v2.key" -out "site_v2.csr" -sha256 -subj '/C=US/ST=CA/L=San Francisco/O=Docker/CN=localhost'

openssl x509 -req -days 750 -in "site_v2.csr" -sha256 -CA "root-ca.crt" -CAkey "root-ca.key" -CAcreateserial -out "site_v2.crt" -extfile "site.cnf" -extensions server

Create new secrets for the updated certificate and key

docker secret create site_v2.crt site_v2.crt

docker secret create site_v2.key site_v2.key

Update the Nginx service to use the new secrets :
 
Remove old secrets and add the new ones.

docker service update \
  --secret-rm site.crt \
  --secret-rm site.key \
  --secret-add source=site_v2.crt,target=/run/secrets/site.crt \
  --secret-add source=site_v2.key,target=/run/secrets/site.key \
  nginx
  
Verify redeployment :

Check that the Nginx service redeployed successfully with the new secrets.

docker service ps nginx

Test HTTPS connection with new certificate :

curl --cacert root-ca.crt https://localhost:3000

openssl s_client -connect localhost:3000 -CAfile root-ca.crt

Remove old secrets once confirmed :

docker secret rm site.crt site.key

Production use case :  
An e-commerce platform rotates TLS certificates every 12 months to maintain secure HTTPS connections. By storing certificates as secrets, they can replace expiring certs (site_v1.crt) with new ones (site_v2.crt) without rebuilding Nginx images or exposing sensitive files. This ensures uninterrupted secure traffic and compliance with industry standards.



WordPress with MySQL Secrets
This example shows how Docker secrets secure database credentials in a real-world stack.

Generate secrets: Random passwords for MySQL (mysql_password for WordPress, mysql_root_password for admin) are created using openssl and stored as secrets.

Overlay network: A private Docker network (mysql_private) is created so MySQL and WordPress can communicate securely without exposing MySQL externally.

MySQL service: Runs with secrets mounted at /run/secrets/. Environment variables point to those secret files, ensuring MySQL initializes with secure credentials. Data persists in a volume (mydata).

WordPress service: Connects to MySQL using the mysql_password secret, avoiding hardcoding credentials in the image or environment variables.

Generate MySQL user password and store as secret

openssl rand -base64 20 | docker secret create mysql_password -

Generate MySQL root password and store as secret

openssl rand -base64 20 | docker secret create mysql_root_password -

List all secrets

docker secret ls

Create private network : Create overlay network for MySQL and WordPress

docker network create -d overlay mysql_private

Create MySQL service : Launch MySQL service with secrets and environment variables

docker service create \
  --name mysql \
  --replicas 1 \
  --network mysql_private \
  --mount type=volume,source=mydata,destination=/var/lib/mysql \
  --secret source=mysql_root_password,target=mysql_root_password \
  --secret source=mysql_password,target=mysql_password \
  -e MYSQL_ROOT_PASSWORD_FILE="/run/secrets/mysql_root_password" \
  -e MYSQL_PASSWORD_FILE="/run/secrets/mysql_password" \
  -e MYSQL_USER="wordpress" \
  -e MYSQL_DATABASE="wordpress" \
  mysql:latest
  
Verify MySQL service is running

docker service ls

Create WordPress service : Launch WordPress service connected to MySQL

docker service create \
  --name wordpress \
  --replicas 1 \
  --network mysql_private \
  --publish published=8080,target=80 \
  --secret source=mysql_password,target=mysql_password \
  -e WORDPRESS_DB_HOST="mysql:3306" \
  -e WORDPRESS_DB_USER="wordpress" \
  -e WORDPRESS_DB_PASSWORD_FILE="/run/secrets/mysql_password" \
  -e WORDPRESS_DB_NAME="wordpress" \
  wordpress:latest
  
Verify WordPress service is running :

docker service ls

docker service ps wordpress

Cleanup :

Remove WordPress service

docker service rm wordpress

Remove MySQL service

docker service rm mysql

Remove secrets

docker secret rm mysql_password mysql_root_password

Remove netw
docker network rm mysql_private

Production use case :  
A SaaS provider hosting multiple WordPress sites uses this workflow to secure MySQL credentials. Secrets ensure passwords aren’t exposed in environment variables or images. When rotating credentials, they simply create new secrets, update services, and remove old ones — keeping downtime minimal and compliance intact.

Secret Rotation in Docker
Why rotate? Secrets like passwords, API keys, or TLS certificates eventually expire or need to be changed for security compliance. Rotation ensures services continue securely without downtime.

Create a new secret: Instead of updating an existing secret (which Docker doesn’t allow), you create a new one with a versioned name, e.g., mysql_password_v2.

openssl rand -base64 20 | docker secret create mysql_password_v2 -

Update the service: Use docker service update to grant the service access to the new secret and remove the old one.

docker service update --secret-rm mysql_password --secret-add mysql_password_v2 wordpress

Redeployment: The service redeploys with the new secret mounted, ensuring containers now use the updated credentials.

Remove old secret: Once all services are confirmed to be using the new secret, you can safely remove the old one.

docker secret rm mysql_password

Best practice: Always version secrets (db_password_v1, db_password_v2) and plan rotations during maintenance windows to avoid unexpected disruptions.

They store each new password as a versioned secret, update dependent services (like WordPress or reporting apps), and remove old secrets once migration is complete. This ensures compliance, minimizes downtime, and prevents stale credentials from lingering in the system.

Check List : 

Preparation

Generate new database password and store as a versioned secret (e.g., mysql_password_v2).

Generate new TLS certificate and key (via OpenSSL or Let’s Encrypt) and store as secrets (site_v2.crt, site_v2.key).

Document the new secret names and ensure they follow a versioning convention.

Update Database Services

Update the MySQL service to remove the old password secret and add the new one.

Update dependent services (e.g., WordPress) to use the new password secret.

Verify redeployment and confirm WordPress can still connect to MySQL.

Update TLS Services

Update the Nginx service to remove old TLS secrets and add the new certificate/key.

Verify redeployment by checking HTTPS connectivity and inspecting the certificate chain.

Confirm that the new certificate is valid and trusted.

Validation

Test application functionality end-to-end (database queries, HTTPS requests).

Check logs for errors in WordPress, MySQL, and Nginx.

Run automated smoke tests to confirm services are healthy.

Cleanup

Remove old secrets (mysql_password, site.crt, site.key) once migration is confirmed.

Update documentation to reflect the new secret versions.

Communicate completion of rotation to stakeholders.

Best Practices

Always schedule rotations during planned maintenance windows.

Use versioned names (v1, v2, v3) for secrets to simplify updates.

Automate rotation with CI/CD pipelines where possible.

Keep root CA and private keys secured outside of Docker.
