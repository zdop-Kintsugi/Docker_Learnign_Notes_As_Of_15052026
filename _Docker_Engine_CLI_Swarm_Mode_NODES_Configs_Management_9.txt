DOCKER CONFIGURATION DATA MANAGEMENT WITH DOCEKR CONFIGS

Docker configs are used to store non-sensitive configuration data (like config files) outside container images.

Difference from secrets: Unlike secrets, configs are not encrypted at rest and are mounted directly into the container filesystem.

Key points:

Configs can be shared across services.

They support strings or binary content up to 500 KB.

Only available for swarm services, not standalone containers.


Configs are stored in the encrypted Raft log (but logs encrypted configs in plain text, replicated across managers).

Mounted as files in containers:

Linux: /<config-name>

Windows: C:\<config-name>

Configs decouple configuration from images → makes images reusable and generic.

Immutable configs → ensures consistency and version control.

Integration with secrets → secure handling of sensitive + non-sensitive data together.

Flexibility → configs can be updated, rotated, or templated without rebuilding images.

Rotation ensures smooth updates without downtime or image rebuilds.


To create a config 

docker config create

To view and inspect the config's configuration

docker config inspect

To list the configs available

docker config ls

To remove the configs

docker config rm


Useful commands to handle deployment with configs 

docker stack deploy

docker stack rm

docker service update


Ownership and permissions can be set (ignored on Windows).

Configs are immutable — to update, create a new config and redeploy.

Nginx with TLS :

This is a more realistic production-style setup where configs and secrets work together.

Generate TLS Certificates :

Use openssl to create a root CA, site key, and site certificate.

Generate a root key.

openssl genrsa -out "root-ca.key" 4096

Generate a CSR using the root key.


openssl req \
         -new -key "root-ca.key" \
         -out "root-ca.csr" -sha256 \
         -subj '/C=US/ST=CA/L=San Francisco/O=Docker/CN=Swarm Secret Example CA'
		 
Configure the root CA. Edit a new file called root-ca.cnf and paste the following contents into it. This constrains the root CA to only sign leaf certificates and not intermediate CAs.


[root_ca]
basicConstraints = critical,CA:TRUE,pathlen:1
keyUsage = critical, nonRepudiation, cRLSign, keyCertSign
subjectKeyIdentifier=hash
Sign the certificate.


openssl x509 -req -days 3650 -in "root-ca.csr" \
              -signkey "root-ca.key" -sha256 -out "root-ca.crt" \
              -extfile "root-ca.cnf" -extensions \
              root_ca
			   
Generate the site key.

openssl genrsa -out "site.key" 4096

Generate the site certificate and sign it with the site key.


openssl req -new -key "site.key" -out "site.csr" -sha256 \
         -subj '/C=US/ST=CA/L=San Francisco/O=Docker/CN=localhost'
		 
Configure the site certificate. Edit a new file called site.cnf and paste the following contents into it. This constrains the site certificate so that it can only be used to authenticate a server and can't be used to sign certificates.


[server]
authorityKeyIdentifier=keyid,issuer
basicConstraints = critical,CA:FALSE
extendedKeyUsage=serverAuth
keyUsage = critical, digitalSignature, keyEncipherment
subjectAltName = DNS:localhost, IP:127.0.0.1
subjectKeyIdentifier=hash
Sign the site certificate.


openssl x509 -req -days 750 -in "site.csr" -sha256 \
   -CA "root-ca.crt" -CAkey "root-ca.key" -CAcreateserial \
   -out "site.crt" -extfile "site.cnf" -extensions server
	
The site.csr and site.cnf files are not needed by the Nginx service, but you need them if you want to generate a new site certificate. Protect the root-ca.key file


Store them as secrets:

docker secret create site.key site.key
docker secret create site.crt site.crt

Create Nginx Config

Save config file (site.conf) with HTTPS settings:

server {
    listen 443 ssl;
    server_name localhost;
    ssl_certificate /run/secrets/site.crt;
    ssl_certificate_key /run/secrets/site.key;
    location / {
        root /usr/share/nginx/html;
        index index.html index.htm;
    }
}

Store it as a Docker config:

docker config create site.conf site.conf

Deploy Nginx Service :

Attach secrets + config:

docker service create \
     --name nginx \
     --secret site.key \
     --secret site.crt \
     --config source=site.conf,target=/etc/nginx/conf.d/site.conf,mode=0440 \
     --publish published=3000,target=443 \
     nginx:latest \
     sh -c "exec nginx -g 'daemon off;'"

Now the container has:

/run/secrets/site.key

/run/secrets/site.crt

/etc/nginx/conf.d/site.conf

Verify Service :

Check service status:

docker service ls

docker service ps nginx

Test HTTPS endpoint:

curl --cacert root-ca.crt https://0.0.0.0:3000

openssl s_client -connect 0.0.0.0:3000 -CAfile root-ca.crt



Config Rotation :

Configs are immutable, so to update:

Create new config (site-v2.conf).

docker config create site-v2.conf site.conf

Update service to use new config.

docker service update \
  --config-rm site.conf \
  --config-add source=site-v2.conf,target=/etc/nginx/conf.d/site.conf,mode=0440 \
  nginx
  
Remove old config.

docker config rm site.conf

Secrets → Secure sensitive files (TLS keys/certs).

Configs → Store non-sensitive settings (Nginx config).

Immutable configs → Rotation ensures smooth updates without downtime.

Decoupling → Same Nginx image can serve multiple sites with different configs.

Why this matters: In production, you don’t want to rebuild images every time configuration changes. Using configs and secrets allows you to:

Run multiple sites with the same Nginx image but different configs.

Securely manage TLS certificates and keys.

Rotate configs seamlessly without downtime.

Outcome: A scalable, secure, and maintainable deployment model where sensitive data (secrets) and non-sensitive configs are managed independently.

services:
  nginx:
    image: nginx:latest
    deploy:
      replicas: 1
    ports:
      - "3000:443"
    secrets:
      - site.key
      - site.crt
    configs:
      - source: site.conf
        target: /etc/nginx/conf.d/site.conf
        mode: 0440
    command: ["nginx", "-g", "daemon off;"]

secrets:
  site.key:
    file: ./site.key
  site.crt:
    file: ./site.crt

configs:
  site.conf:
    file: ./site.conf

Nginx Configs for Each Site 

site1.conf
server {
    listen 443 ssl;
    server_name site1.com;
    ssl_certificate /run/secrets/site1.crt;
    ssl_certificate_key /run/secrets/site1.key;

    location / {
        root /usr/share/nginx/html/site1;
        index index.html;
    }
}

site2.conf
server {
    listen 443 ssl;
    server_name site2.com;
    ssl_certificate /run/secrets/site2.crt;
    ssl_certificate_key /run/secrets/site2.key;

    location / {

}

Create secrets for each cert/key pair:

docker secret create site2.key site2.key

Step‑by‑Step Rotation Workflow :

Update Config Files
Edit your Nginx site config (site1.conf, site2.conf) locally.

Example: add support for index.php or update TLS settings.

server {
    listen 443 ssl;
    server_name site1.com;
    ssl_certificate /run/secrets/site1.crt;
    ssl_certificate_key /run/secrets/site1.key;

    location / {
        root /usr/share/nginx/html/site1;
        index index.html index.htm index.php;
    }
}

Create New Configs
Save updated configs with new names (e.g., site1-v2.conf, site2-v2.conf).

Create them in Docker:

docker config create site1-v2.conf site1.conf
docker config create site2-v2.conf site2.conf

Rotate Certificates (Secrets)
When certs expire, generate new ones (site1-new.crt, site1-new.key).

Create new secrets:

docker secret create site1-new.crt site1-new.crt
docker secret create site1-new.key site1-new.key

Update Service
Redeploy service with new configs and secrets:

docker service update \
  --config-rm site1.conf \
  --config-add source=site1-v2.conf,target=/etc/nginx/conf.d/site1.conf,mode=0440 \
  --secret-rm site1.crt \
  --secret-rm site1.key \
  --secret-add source=site1-new.crt,target=site1.crt \
  --secret-add source=site1-new.key,target=site1.key \
  nginx


Verify Redeployment :

Check service status:

docker service ps nginx

Test endpoints with updated certs:

curl --cacert new-root-ca.crt https://site1.com

curl --cacert new-root-ca.crt https://site2.com


Clean Up Old Configs/Secrets
Once redeployment is stable, remove old configs and secrets:

docker config rm site1.conf site2.conf
docker secret rm site1.crt site1.key site2.crt site2.key
