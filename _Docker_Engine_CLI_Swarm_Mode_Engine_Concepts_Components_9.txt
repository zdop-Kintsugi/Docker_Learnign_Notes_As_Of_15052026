DOCKER ENGINE SWARM MODE CONCEPTS PARTS

Swarm Mode Key Concepts

This section introduces the main ideas behind Docker Swarm mode, which is Docker’s built-in tool for cluster management and container orchestration. It explains how multiple Docker hosts can work together as a single system. Swarm mode helps automate deployment, scaling, networking, and management of containers. It is powered internally by SwarmKit, a separate orchestration project used by Docker. The section also introduces important concepts like nodes, services, tasks, and load balancing. Docker ensures the desired state of applications by automatically recovering failed tasks. Swarm mode also allows updating services without manually restarting containers. Overall, this section gives a foundation for understanding Docker clustering and orchestration.

Swarm :

A swarm is a group of Docker hosts connected together and running in Swarm mode. These hosts can act as managers, workers, or both. Manager nodes control the cluster and assign tasks, while worker nodes execute the tasks. A service defines the desired state of an application, such as the number of replicas, ports, and storage settings. Docker continuously checks and maintains this desired state automatically. If a node fails, Docker redistributes tasks to healthy nodes. Swarm services are different from standalone containers because they are managed centrally by swarm managers. Swarm mode also supports rolling updates, meaning services can be updated without downtime. This section explains the overall architecture and benefits of Docker Swarm.

Nodes :

A node is any machine running Docker Engine and participating in the swarm cluster. Nodes can be physical servers, virtual machines, or cloud instances. There are two main types of nodes: manager nodes and worker nodes. Manager nodes handle orchestration tasks like scheduling and maintaining the cluster state. Worker nodes execute the tasks assigned by managers. By default, manager nodes can also run workloads like workers. Each worker has an agent that reports task status back to the manager. Managers elect a leader node to coordinate orchestration activities. Production environments usually distribute nodes across multiple machines for better reliability and scalability. This section focuses on how swarm nodes cooperate to keep applications running smoothly.

Services and Tasks :

A service is a definition of how containers should run inside the swarm cluster. It specifies details like the container image, commands, replicas, and networking settings. Services are the main way users interact with Docker Swarm. In replicated mode, Docker runs a specified number of copies (replicas) across available nodes. In global mode, one task runs on every node automatically. A task is the smallest scheduling unit in Swarm and represents a running container plus its instructions. Tasks are assigned by manager nodes to worker nodes. Once assigned, a task cannot move to another node; it either runs successfully or fails. Swarm continuously monitors tasks and replaces failed ones when necessary. This section explains how Docker manages distributed workloads efficiently.

Load Balancing :

Docker Swarm provides built-in load balancing so that traffic can automatically reach the correct containers running across the cluster. This is one of the most important production features because users should be able to access services without caring which node or container is actually serving the request.

Docker Swarm includes built-in load balancing to distribute traffic among service containers. The swarm manager exposes services externally using ingress load balancing. Each service can have a published port, either manually specified or automatically assigned by Docker. External users can access the service from any node in the cluster, even if that node is not running the service task. The swarm routes incoming requests internally to an active container instance. Swarm also provides internal DNS-based load balancing between services. Every service gets its own DNS entry for easy communication inside the cluster. This helps applications communicate reliably without manual network configuration. Load balancing improves availability, scalability, and efficient traffic distribution across the swarm.


Ingress Load Balancing?

Ingress load balancing is Docker Swarm’s routing mesh mechanism.

It allows:

Any node in the swarm to accept incoming traffic
Traffic to automatically route to the correct service container
Services to remain accessible even if containers move between nodes
Example

Suppose you have :

3 swarm nodes:
Node1
Node2
Node3

Your web application container runs only on:

Node2

But users can still access:

http://Node1:80
http://Node2:80
http://Node3:80

Even though the container exists only on Node2 we need it; because Docker Swarm’s routing mesh forwards requests internally to the active container.

Published Port Concept :

When deploying a service:

docker service create \
  --name web \
  --publish 80:80 \
  nginx

Docker exposes:

HOST_PORT:CONTAINER_PORT
80:80

Meaning:

Port 80 on swarm nodes
forwards traffic to
Port 80 inside containers

Automatic Port Assignment :

If you do not specify a port:

docker service create nginx

Docker automatically assigns one between:

30000–32767

Example:

PublishedPort = 30012

This is similar to Kubernetes NodePort behavior.

Routing Mesh (VERY IMPORTANT) :

Routing mesh is the heart of swarm networking.

How it works

When a request arrives:

Client → Any Swarm Node → Routing Mesh → Correct Container

Docker uses:

IPVS
iptables
VXLAN overlay networking

To route packets internally.

Real Production Flow :

Example production architecture:

Internet
   ↓
Cloud Load Balancer (AWS ELB / Nginx / HAProxy)
   ↓
Any Swarm Node
   ↓
Routing Mesh
   ↓
Running Container

This gives:

High availability
Automatic failover
Easy scaling
Zero downtime deployments

Internal DNS Load Balancing

Swarm also has internal service discovery.

Every service automatically gets a DNS name.

Example:

docker service create --name backend redis

Other containers can connect using:

backend

instead of IP addresses.

Docker internally resolves:

backend → container IPs

Internal Service Communication :

Example:

Frontend Service → backend:6379

Docker DNS automatically:

Finds backend containers
Balances requests
Updates IPs dynamically

This avoids hardcoding IP addresses.

VIP (Virtual IP) Load Balancing :

By default, Docker creates:

Virtual IP (VIP)

for every service.

Example:

backend → 10.0.0.5

Docker balances traffic across replicas behind this VIP.

Important Production Concepts :
A. Any Node Can Receive Traffic

VERY IMPORTANT:

Even if no container runs on a node:

Node accepts traffic anyway

Because of routing mesh.


B. Overlay Network Required

Routing mesh depends heavily on:

Overlay networks
VXLAN tunneling

Required ports:

Port	Purpose
2377	Cluster management
7946 TCP/UDP	Node communication
4789 UDP	Overlay/VXLAN traffic

If these ports are blocked:

routing mesh fails
containers cannot communicate


Stateful Applications Warning

Routing mesh is not always ideal for:

databases
sticky sessions
WebSocket-heavy apps

Why?

Traffic may hit different replicas.

For databases:

Use:

--endpoint-mode dnsrr

Instead of VIP mode.


Real Production Best Practices :
Use External Load Balancer

In production:

DO NOT expose nodes directly.

Instead use:

AWS ELB
Nginx
HAProxy
Traefik

in front of swarm.

Separate Manager and Worker Nodes

Managers should ideally:

manage cluster only
not serve heavy traffic

Reason:

Heavy traffic can impact orchestration stability.

Monitor Overlay Network

Monitor:

VXLAN latency
packet drops
MTU mismatch
DNS resolution delays

because overlay networking adds overhead.


Common Routing Mesh Troubleshooting
Problem 1: Service Not Reachable
Symptoms
Connection timeout
Check
Verify service
docker service ls
Check tasks
docker service ps web
Check published ports
docker service inspect web
Problem 2: Overlay Network Failure
Symptoms
Containers cannot talk
DNS resolution fails
Cross-node communication broken
Check firewall ports

Must open:

2377 TCP
7946 TCP/UDP
4789 UDP
Problem 3: DNS Resolution Failure
Symptoms
ping backend → fails
Troubleshooting

Check:

docker network inspect <network>

Verify services attached correctly.

Problem 4: Traffic Only Works on One Node

Usually caused by:

Routing mesh disabled
Firewall issue
Cloud security groups blocking ports

Especially:

4789 UDP
Problem 5: MTU Mismatch

Very common in cloud environments.

Symptoms
Random packet drops
Slow responses
Intermittent failures

Overlay networking adds VXLAN headers.

Fix by reducing MTU:

Example:

docker network create \
  --opt com.docker.network.driver.mtu=1450
